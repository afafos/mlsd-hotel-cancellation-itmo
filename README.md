# Прогноз риска отмены бронирования отеля

Проект по ML System Design (ИТМО). Сервис каждое утро оценивает вероятность отмены или неявки для активных броней отеля и формирует для администратора короткий список: какие брони стоит подтвердить в первую очередь.

Подробный дизайн решения — в [docs/ml_system_design_doc.md](docs/ml_system_design_doc.md).

Выполнены аудит, EDA (включая анализ признаков на ежедневных снимках) и бейзлайны B0/B1; описаны подготовка данных, моделей и дальнейшие этапы.
Результаты анализа с графиками и выводами — в [reports/eda/README.md](reports/eda/README.md), метрики бейзлайнов — в [reports/baselines/README.md](reports/baselines/README.md).

## Задача

- **Для кого:** администраторы ресепшена и revenue-менеджер отеля.
- **Проблема:** 37% броней в данных заканчиваются отменой или no-show. Позднюю отмену (за ≤ 7 дней до заезда) или неявку труднее компенсировать повторной продажей. Стоимость таких броней — ≈ 76 тыс. у.е. в месяц на два отеля по приближению ADR × число ночей. Это сумма под риском, а не измеренные потери выручки: данных о возвратах и перепродаже нет.
- **Решение:** ежедневно ранжировать активные брони с заездом в ближайшие 14 дней по вероятности отмены и выдавать по каждому отелю топ-20 с причинами риска.
- **Как измеряем:** Precision@20, Recall@20 и Lift@20 по каждому отелю и дню на отложенном периоде (май–август 2017), PR-AUC, калибровка. Критерий успеха MVP — Lift@20 ≥ 3 в каждом отеле и превосходство над сильнейшим правилом B1+t (историческая доля отмен сегмента с учётом дней до заезда). На valid текущая практика «сначала ближайшие заезды» даёт Lift@20 0,4–0,8, B1+t — 1,8–2,8; обоснование порога — в этапе 2 дизайн-документа.
- **Главные нюансы:**
  - модель должна видеть только то, что известно утром в день построения списка; публичный CSV не содержит полной истории изменений, поэтому восстановленные снимки — приближение для исследования
  - в восстановленных дневных списках мая–августа 2017 будущих отмен 4–5%, а не 37%, как по всему датасету, т.к. большинство отмен случается за месяцы до заезда.

## Данные

[Hotel Booking Demand](https://doi.org/10.1016/j.dib.2018.11.126) (Antonio, de Almeida, Nunes, 2019) — 119 390 броней городского и курортного отелей в  Португалии с заездами с июля 2015 по август 2017, включая отменённые.
Описание полей — в [словаре TidyTuesday](https://github.com/rfordatascience/tidytuesday/tree/main/data/2020/2020-02-11).

Данные не хранятся в репозитории: `make data` скачивает CSV из закреплённого коммита TidyTuesday в `data/raw/`.

## Как запустить

Нужны [uv](https://docs.astral.sh/uv/getting-started/installation/) и `make`; Python 3.12 uv установит сам, если его нет.

```bash
git clone https://github.com/afafos/mlsd-hotel-cancellation-itmo.git
cd mlsd-hotel-cancellation-itmo
make install   # .venv с зависимостями из uv.lock и pre-commit-хуки
make data      # скачать датасет в data/raw/ и проверить SHA-256
make audit     # вывести факты о данных, на которые опирается дизайн-документ
make eda       # пересоздать таблицы и графики отчета reports/eda/
make baselines # бейзлайны B0/B1 на valid и бэктестах 2016 года в reports/baselines/
make test      # проверить снимки, временные выборки, метрики top-K и бейзлайны
```

В `make audit`, `make eda` и `make baselines` нет случайности: случайный порядок в бейзлайнах считается как математическое ожидание. При неизменных данных и зависимостях численные результаты воспроизводятся. `make eda` и `make baselines` проверяют SHA-256 исходного файла и сохраняют агрегированные CSV и PNG; готовые отчёты по [EDA](reports/eda/README.md) и [бейзлайнам](reports/baselines/README.md) можно читать без запуска Python. Исходный CSV и строки отдельных броней в Git не добавляются. Модели B2 и CatBoost появятся на следующих этапах: у каждой будет своя команда в этом разделе и фиксированный random seed = 42.

EDA включает состав всех полей, пропуски, дубликаты, аномалии и согласованность разметки, сроки отмен, сезонность, сегменты и ежедневные списки. Отдельно разобраны сигнал признаков на снимках, корреляции и мультиколлинеарность, влияние повторов на признаки и сегменты, связь порядка строк с меткой и готовность меток на временных границах. Статистики позднего периода уже исследованы, поэтому test нельзя считать полностью нетронутым. Новые анализы и бейзлайны используют только train/valid: на test не посчитано ни одной метрики ранжирования.

Для разработки:

```bash
make lint      # ruff и mypy без изменения файлов
make format    # исправить замечания ruff и отформатировать код
make check     # все pre-commit-хуки на всех файлах — то же, что запускает CI
```

Без `make` те же команды запускаются через `uv run`, например `uv run python -m hotel_cancellation.audit`.

## Структура репозитория

```text
.
├── docs/
│   └── ml_system_design_doc.md   # дизайн-документ ML-системы
├── reports/
│   ├── eda/                      # EDA: README с графиками и выводами, figures/, tables/
│   └── baselines/                # бейзлайны B0/B1: README, figures/, tables/
├── src/hotel_cancellation/
│   ├── data.py                   # загрузка датасета и производные даты
│   ├── snapshots.py              # ежедневные снимки активных броней — единица прогноза
│   ├── audit.py                  # факты о данных для дизайн-документа
│   ├── eda.py                    # воспроизводимый анализ и визуализации
│   ├── feature_eda.py            # признаки на снимках, корреляции, повторы, порядок строк
│   ├── metrics.py                # Precision/Recall/Lift@K с равенствами, AP, ROC-AUC
│   ├── baselines.py              # B0/B1 на valid и бэктестах; test-период запрещён
│   └── report.py                 # общие функции сохранения таблиц и графиков
├── tests/                        # снимки, временные выборки, метрики и бейзлайны
├── .github/workflows/ci.yml      # CI: pre-commit и тесты на push в main и pull request
├── .pre-commit-config.yaml       # хуки: ruff, mypy и базовые проверки файлов
├── Makefile                      # короткие команды
├── pyproject.toml                # зависимости и настройки ruff и mypy
└── uv.lock                       # зафиксированные версии зависимостей
```
