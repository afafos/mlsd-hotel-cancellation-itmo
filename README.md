# Прогноз риска отмены бронирования отеля

Проект по ML System Design (ИТМО). Сервис каждое утро оценивает вероятность отмены или неявки для активных броней отеля и формирует для администратора короткий список: какие брони стоит подтвердить в первую очередь.

Подробный дизайн решения — в [docs/ml_system_design_doc.md](docs/ml_system_design_doc.md).

## Задача

- **Для кого:** администраторы ресепшена и revenue-менеджер отеля.
- **Проблема:** 37% броней в данных заканчиваются отменой или no-show. Дороже всего поздние потери — отмена за ≤ 7 дней до заезда или неявка: номер не успевают продать повторно. Это ≈ 76 тыс. у.е. выручки в месяц на два отеля, а подтвердить все брони администратор не успевает.
- **Решение:** ежедневно ранжировать активные брони с заездом в ближайшие 14 дней по вероятности отмены и выдавать по каждому отелю топ-20 с причинами риска.
- **Как измеряем:** Precision@20, Recall@20 и Lift@20 по каждому отелю и дню на отложенном периоде (май–август 2017), PR-AUC, калибровка. Критерий успеха MVP — Lift@20 ≥ 3 и превосходство над бейзлайном "историческая доля отмен сегмента".
- **Главные нюансы:**
  - модель видит только то, что известно утром в день построения списка
  - в реальном дневном списке будущих отмен 4–5%, а не 37%, как по всему датасету, т.к. большинство отмен случается за месяцы до заезда.

## Данные

[Hotel Booking Demand](https://doi.org/10.1016/j.dib.2018.11.126) (Antonio, de Almeida, Nunes, 2019) — 119 390 броней городского и курортного отелей в  Португалии с заездами с июля 2015 по август 2017, включая отменённые.
Описание полей — в [словаре TidyTuesday](https://github.com/rfordatascience/tidytuesday/tree/main/data/2020/2020-02-11).

Данные не хранятся в репозитории: `make data` скачивает CSV из закреплённого коммита TidyTuesday в `data/raw/`.

## Как запустить

Нужны [uv](https://docs.astral.sh/uv/getting-started/installation/) и `make`; Python 3.12 uv установит сам, если его нет.

```bash
git clone https://github.com/afafos/mlsd-hotel-cancellation-itmo.git
cd mlsd-hotel-cancellation-itmo
make install   # .venv с зависимостями из uv.lock и pre-commit-хуки
make data      # скачать датасет в data/raw/ и проверить SHA-256
make audit     # вывести факты о данных, на которые опирается дизайн-документ
```

В `make audit` нет случайности: при каждом запуске он печатает одни и те же числа — те, что приведены в дизайн-документе. Эксперименты с моделями (бейзлайны, CatBoost) появятся на следующих этапах: у каждого будет своя команда в этом разделе и фиксированный random seed.

Для разработки:

```bash
make lint      # ruff и mypy без изменения файлов
make format    # исправить замечания ruff и отформатировать код
make check     # все pre-commit-хуки на всех файлах — то же, что запускает CI
```

Без `make` те же команды запускаются через `uv run`, например `uv run python -m hotel_cancellation.audit`.

```text
├── docs/

├── Makefile                      # короткие команды
├── pyproject.toml                # зависимости и настройки ruff и mypy
└── uv.lock                       # зафиксированные версии зависимостей
```
